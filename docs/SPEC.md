# cc-sidebar: Spec

Status: v0.3 (2026-10-17): app v0.2.0 installed; M0–M9 done. Items marked **[verify]** are assumptions from the docs that a spike must confirm.

## 1. Problem

The user runs many interactive Claude Code sessions at once, across several projects, in Windows Terminal tabs (Claude Code runs inside WSL). There's lots of screen space but no at-a-glance view of which sessions are working, which are blocked waiting for input, and which hit trouble. Finding the right tab is slow.

## 2. Goals

1. A sidebar permanently docked to one screen edge, reserving its space like the taskbar does.
2. One card per active session, stacked vertically. You can tell the project apart instantly.
3. Each card shows live status and a recap of what the session is doing or just did.
4. Clicking a card focuses that session's Windows Terminal tab. If the tab is gone, it resumes the session in a new tab.
5. Loud, obvious feedback when things go wrong: auto-mode denials, failures, stuck or waiting sessions.
6. Actions from the card: approve/deny permission prompts, send a prompt, resume, kill.

Non-goals (for now): macOS/Linux support, multi-machine, editing code, replacing the terminal UI.

## 3. Architecture

```
WSL                                             Windows
───────────────────────────────                 ─────────────────────────────────────────
cc (wrapper) ─exec─> claude ─cc-hook shim──────> Tauri app (Rust)
   sets env tag,        │                         ├─ hook server  <wsl-host-ip>:47821
   tab title            │ spawns (stdio)          ├─ session store + state machine
                        └─> cc-channel (MCP) <──> ├─ channel hub (WebSocket)
                                                  ├─ recap worker (instant + Haiku)
                                                  ├─ AppBar docking (Win32)
                                                  ├─ UI Automation (focus WT tab)
                                                  └─ WebView UI (React)
```

### 3.1 Session launcher: `claudes` wrapper (WSL)

Named `claudes`, not `cc` as first planned: `cc` is the C compiler and `~/.local/bin` comes first on PATH (found at install, 2026-10-17).

A small script used instead of `claude`. Plain `claude` still works, with fewer features (see 3.8).

- Generates `CC_SIDEBAR_TAG` (short random id) and exports `CC_SIDEBAR_PID=$$`, then `exec claude --channels <our channel> "$@"`. Because of `exec`, the PID stays the claude process.
- Sets `CLAUDE_CODE_DISABLE_TERMINAL_TITLE=1` and writes the tab title via OSC 0: `[cc:<tag>] <project>`. Verified in S2: it survives idle, working and done.
- `WT_SESSION` is inherited unchanged (Windows Terminal already sets it per pane), and `cc-hook` forwards it as well.

### 3.2 Hooks → app

**Decision (2026-10-17): WSL stays on NAT networking.** The machine runs Tailscale and several VPNs, and mirrored mode is known to clash with VPN software. So hooks can't use `localhost`; they reach the Windows app through the WSL→host IP.

Transport: **command hooks running a tiny shim** (`cc-hook`, installed in WSL), not HTTP hooks. Per event, the shim:

1. Resolves the Windows host IP from the default route (`ip route show default`), cached in `$XDG_RUNTIME_DIR` and re-resolved if a connect fails (the IP can change across reboots).
2. Pipes the hook's stdin JSON to `curl -s --max-time <t> -H 'X-CC-Tag: …' … http://<host-ip>:47821/hook` and prints the response body to stdout, so blocking hooks (PermissionRequest) can still return a decision.
3. Exits 0 with empty output on any failure (app down, timeout), so Claude is never blocked or slowed beyond the timeout.

Because the shim is a normal process in the session's environment, it reads `CC_SIDEBAR_TAG`, `CC_SIDEBAR_PID`, `WT_SESSION` and `CC_SIDEBAR_INTERNAL` directly. No `allowedEnvVars` header forwarding is needed.

```jsonc
// shape per event; generated by a script, not hand-written
{ "type": "command", "command": "cc-hook", "timeout": 5 }   // PermissionRequest: longer timeout, see 3.6
```

- The app's server binds the WSL vEthernet adapter address (the host IP above), plus `127.0.0.1` for local tools. It is not bound to all interfaces, so it isn't reachable over Tailscale or a VPN.
- Events: `SessionStart`, `SessionEnd`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `PermissionRequest`, `PermissionDenied`, `Notification`, `Stop`, `StopFailure`, `PreCompact`, `CwdChanged`, `SubagentStart`/`SubagentStop`.
- Non-blocking hooks must never slow Claude down: short curl timeouts, always exit 0.
- Events carrying `X-CC-Internal: 1` (our own Haiku calls) are dropped, to avoid recursion.
- *M0 probe:* under NAT, a Windows listener on `localhost` is unreachable from WSL. A Windows `TcpListener` on the host IP `172.25.192.1:47821` received a `curl` from WSL and returned 200, with no firewall rule added. powershell.exe already had a rule; a new exe triggers the firewall's "allow public and private networks" prompt (S1). The installer must add a port-scoped inbound rule (TCP 47821, WSL interface only) so no build prompts.
- Measured in S1: 10–20 ms per event (process spawn plus curl). Still **[verify]** during dogfooding: the host IP stays stable through sleep/resume and VPN connect/disconnect.

### 3.3 Session model (Rust)

Key: `session_id`. Fields: tag, pid, wt_session, cwd, project (root, name, colour), branch, permission_mode, model, status, current tool, last prompt, recap (instant and haiku), alerts[], pending permission, timestamps (started, last event, status since), transcript_path.

Status state machine:

| Status | Entered on | Card |
|---|---|---|
| `starting` | SessionStart | grey |
| `working` | UserPromptSubmit, PreToolUse, SubagentStart | animated; shows the current tool ("Editing auth.ts") |
| `needs_permission` | PermissionRequest, or Notification `permission_prompt` | amber, pulsing; approve/deny buttons |
| `needs_input` | AskUserQuestion, ExitPlanMode, an interrupt, a permission declined in the terminal; Notification `elicitation_dialog` / `agent_needs_input` (not `idle_prompt`) | amber |
| `idle` | Stop | green "ready" plus recap |
| `error` | StopFailure | red ⚠️ |
| `closed` | SessionEnd (`/exit` → reason `prompt_input_exit`; closing the tab → reason `other`), or PID gone without SessionEnd (crash, kill) | dimmed, in a "Closed" group at the bottom; click resumes it in a new tab |
| (removed) | dismissed by the user; auto-pruned after 7 days closed (configurable); or SessionEnd reason `clear` (the session is replaced by a new one) | card fades out |

Decision (2026-10-17): sessions stay visible after Claude Code exits, so they can be resumed. Closed sessions are saved to `%APPDATA%\cc-sidebar\sessions.json` so they survive app restarts. If a closed session is resumed with the same `session_id`, its card comes back to life.

Event quirks (S1): ignore `SubagentStart`/`SubagentStop` with empty `agent_type` (Claude Code's internal helper agents). `Stop` with non-empty `background_tasks` means idle with a subagent still running, so show that rather than "ready". `idle_prompt` was not observed in testing at first; since 2026-10 Claude Code sends it a minute after every finished turn, so it's ignored (a finished turn stays ready).

Alerts are separate from status, sticky until clicked or dismissed, and shown as an emoji badge with a flash animation:

- 🚫 `PermissionDenied` (auto-mode block). Shows the tool and a short form of the input, plus `reason`, which holds the classifier's category, e.g. `[Auto-Mode Bypass]` (S4).
- ⚠️ `StopFailure`
- 🔁 3+ consecutive `PostToolUseFailure` events for the same tool
- ⏳ `needs_permission` / `needs_input` unanswered for more than 2 min (configurable)
- 🐌 working with no events for more than 10 min
- 📦 `PreCompact` (context filling up), informational

Liveness: with `CC_SIDEBAR_PID` known, check every 30 s via a single batched `wsl.exe -d <distro> -e sh -c 'for p in …; do [ -d /proc/$p ] || echo $p; done'`. Never one call per session. Always call WSL with `-e`: with `--`, the default shell re-parses the joined command line and quoting is lost (M2).

### 3.4 Project identity

- Project root: walk up from `cwd` to the nearest `.git`, reading the files through `\\wsl.localhost\<distro>\…` from Rust (no `wsl.exe` call needed). Worktrees: resolve the `.git` file's `gitdir:` back to the main repo, and show the worktree name.
- Branch: read `.git/HEAD`, refreshed on Stop and CwdChanged.
- Colour: stable hash of the root path into a curated palette of 12 colours that are distinct in both light and dark themes. Shown as a thick left band plus a tinted header.
- Optional overrides in `%APPDATA%\cc-sidebar\projects.toml`: display name, colour, emoji, a short label.
- Cards group by project when several sessions share one (thin group header).
- Dev config: `launcher = "/mnt/c/dev/cc-sidebar/dev/bin/claudes"` with `CC_SIDEBAR_SETTINGS` in `[launch_env]` so resumed test sessions load the test hooks. At install (M7) this becomes `launcher = "claudes"`.

### 3.5 Recaps

**Since 2026-10-21 the card shows Claude's last answer, not a summary.** The user found Haiku over-summarised, and what they want is the last action. `Stop.last_assistant_message` is kept as plain text (`answer_text`: Markdown markers removed, bullets as •). The card shows its first 5 lines and the hover copy 12, blank lines left out. A question it ends on (`ending_question`) is pinned under it. Old cards get theirs from the transcript at startup.

Haiku now runs only when a session has background commands to label as job or service (`BACKGROUND:`) or has no title yet. Otherwise a turn just refreshes the usage numbers if they're over 5 minutes old (`cc-usage`). The Haiku line it still writes isn't shown. The original design follows.

- **Instant** (under 100 ms, on Stop): last user prompt (truncated) plus the first sentence of the last assistant message. `Stop` carries `last_assistant_message` (S1), so no transcript read is needed. The last user prompt comes from `UserPromptSubmit`; skip prompts starting `<agent-message` (subagent hand-backs).
- **Haiku** (async, on Stop, debounced): take the last ~20 transcript entries, condensed, and ask for a one-line recap (max ~90 chars) plus a 2–3 line detail for hover or expand. Swap it in when it arrives.
  - Runner, chosen by the auth type (see env check): with a claude.ai login, `wsl.exe -- bash -l recap.sh <transcript>`, which runs `CC_SIDEBAR_INTERNAL=1 claude -p --model haiku --no-session-persistence --tools "" --strict-mcp-config --setting-sources "" --system-prompt …` with the condensed transcript on stdin. Measured 5.7–6.3 s, no transcript left behind, no hooks loaded (S7). Option (b), the API with a stored key, is not needed.
  - Cap: at most one in flight per session, at most 2 overall, and at least `recap_min_interval_s` (30 s) between runs for a session; a result applies only to the Stop it was made for (`stop_seq`). Script: `cc-recap` (dev: `dev/bin/cc-recap`), configured by `recap_command` ("" disables).

### 3.6 Actions

| Action | Mechanism |
|---|---|
| Focus | UI Automation: find the WT window and tab whose name contains `[cc:<tag>]`, select it, `SetForegroundWindow` with the alt-key trick. Verified in S2: 130–590 ms, works while another app has focus. Restoring from minimised is not yet tested. |
| Resume (tab gone) | `wt.exe -w <terminal_window> new-tab --title "[cc:<tag>] <project>" wsl.exe -d <distro> --cd <cwd> -- bash -lc "claudes --resume <session_id>"` |
| Approve / Deny | `PermissionRequest` hook request (via `cc-hook`) held open by the server. The terminal prompt is shown **at the same time** (S3), and whichever answers first wins. A sidebar click answers `{"hookSpecificOutput":{"hookEventName":"PermissionRequest","decision":{"behavior":"allow"}}}` (or `deny` + `message`), which closes the terminal prompt. If the user answers in the terminal, Claude Code kills the hook, so the server sees the connection drop and clears the card. Hook timeout ~590 s / shim limit ~580 s, so the buttons stay live while the prompt is up. On timeout, nothing is decided and the prompt stays. No hold window and no "answer in terminal" button. |
| Send prompt | **Deferred** (2026-10-17): needs channels (3.7), which the org policy disables. |
| End | `wsl.exe -e kill -TERM <pid>` after a two-click confirm; gives a clean SessionEnd. There is no "interrupt the current turn": SIGINT also ends claude, and the TUI's Ctrl+C/Esc are keypresses (no injection). |
| Open folder | Explorer, or VS Code (`code --remote wsl+<distro> <cwd>`). |

### 3.7 Channel: `cc-channel`

- A small stdio MCP server (TypeScript, Node, runs in WSL), declared as a Claude Code channel per the channels reference. During development it loads via `--dangerously-load-development-channels`; later it's packaged as a local plugin.
- On start it connects to `ws://<wsl-host-ip>:47821/channel` (same host-IP resolution as `cc-hook`) and registers with its parent PID (`process.ppid`, which is the claude process) and `CC_SIDEBAR_TAG`. The hub joins it to the session through the PID/tag also sent in hook headers. Verified in S5: `process.ppid` is the claude PID and the tag is inherited.
- **Blocked (S5):** on this Claude org, channels are disabled by policy (`channelsEnabled` must be set by an admin in managed settings). Until that changes, pushed messages are silently dropped. Decision (2026-10-17): skip send-prompt for now. The `claudes` wrapper does not pass `--channels`, and this section is kept for a later revisit.
- Pushes sidebar prompts into the session as channel messages. If the channel supports permission relay, evaluate it as an alternative to the PermissionRequest hold.
- Read the official channels reference before building. Requires claude.ai login auth.

### 3.8 Plain `claude` sessions (no wrapper)

These still appear (hooks are global after install) but have no tag, PID or channel. That means status and recap work, and focus falls back to matching tabs by project name (rarely works in practice: plain `claude` titles its tab with a task summary), else the card explains how to restart it with `claudes --continue`. Send-prompt and kill are disabled, and a hint on the card says "start with `claudes` for full controls".

### 3.9 Sidebar UI

- Window modes (M9): `mode = "docked"` (AppBar, below) or `"floating"` (a normal frameless, movable, resizable window that reserves no space; position saved in `ui.json`). `monitor = 0` = primary, n = nth from the left. Collapse (» / tray) shrinks either mode to a 30 DIP status strip with one dot per project.
- AppBar via `SHAppBarMessage` (ABM_NEW / ABM_QUERYPOS / ABM_SETPOS). Handle `ABN_POSCHANGED`, DPI changes and monitor changes. Borderless, no taskbar button, and a tray icon for settings and quit.
- Card (around 110 px collapsed):
  - colour band
  - project name and branch
  - status chip with an elapsed timer
  - recap line
  - alert badges
  - hover or expand for detail recap, last prompt and action buttons
- Ordering: needs-attention first (permission or alerts), then working, then idle. Within each group, keep a stable order by start time. No jumping around while the mouse is over the sidebar.
- Notification sound per alert type (`[sounds]` in config: system sound alias, .wav path or ""), Windows toast when the sidebar is hidden (`toasts = "when_hidden"`: a full-screen app covers it; or "always"/"never"), and a global hotkey (`jump_hotkey`, default Ctrl+Alt+J) to focus the session waiting on you longest. New alerts flash their card for 4 s.
- A "ready" pill fades from green to grey between 1 and 2 hours of the user being **at the computer** since it became ready. Away spells (5 minutes with no keyboard or mouse input, a locked screen, sleep, the computer off) don't count, so a session finished just before lunch or the end of the day is still green on return. The timer on the pill shows real time.
- Theme follows Windows light/dark.

### 3.10 Config

`%APPDATA%\cc-sidebar\config.toml`: edge, monitor, width, port, WSL distro, hold window, stale thresholds, sounds, recap runner. Hot-reloaded.

Edited from a **settings window** (⚙ → Settings…, or the tray), with General, Alerts, Projects and Advanced tabs. It covers config.toml and projects.toml (per-project name, label, emoji, colour and task source). Save writes only what changed into the files, keeping their comments; the file watcher applies it as it would a hand edit. The files stay the source of truth and can still be edited by hand.

### 3.11 Add project (2026-10-17; was "new session")

The footer's **+** (the sidebar has no header since 2026-10-22: its +, ⚙ and collapse buttons sit beside the usage bars, and a floating window is dragged by the footer) adds a project (tracked, no session) from recents not already in the sidebar, or any folder; sessions start from the project's own **+**. Original design:

A "+" button in the sidebar header opens a project picker:

- **Recents:** project roots from current and closed sessions, plus the `cwd` recorded in recent transcripts under `~/.claude/projects/*/*.jsonl` (read via `\\wsl.localhost`), most recent first.
- **Other…:** type a WSL path (with completion) or pick a folder in the Windows folder dialog (`\\wsl.localhost\<distro>\…` paths are mapped back to Linux paths).
- Launch: `wt.exe -w 0 new-tab --title "[cc:<tag>] <project>" wsl.exe -d <distro> --cd <path> -e bash -lc cc`, then the new card appears from its SessionStart.

### 3.12 Projects, sessions and tasks (M8, 2026-10-17)

Decisions (2026-10-17): stable project order with drag to reorder; trackers via Claude + claude.ai connectors; hover flyout for details; starred sessions at the top of their project.

- **Projects are first class.** The sidebar is a list of project sections, each listing its sessions. A project is tracked automatically when its first session appears and stays (persisted in `%APPDATA%\cc-sidebar\projects.json`) when it has none. Order is stable: new projects go to the bottom, and headers are dragged to reorder; nothing reorders itself. A project with a session needing attention shows it in its header (status dot + flash) instead of moving.
- **Drawer:** a project can be put away (⋯ → Put in drawer, or drag its header to the bottom). It becomes a small square tile on a shelf at the bottom of the sidebar, keeping its status dot and flash, and comes back with a click or a drag. Starting a new session in it takes it out of the drawer.
- **Waiting on background work:** jobs Claude started in the background and will act on (a watcher, a poll loop, a background agent) are shown in a highlighted "Waiting on" block on the card, apart from services such as dev servers. Each is guessed from its description, then confirmed or overruled by Haiku's `WAITING:` verdict. When a job reports back and Claude has dealt with it, a ✅ alert sounds straight away (unless the user started that turn).
- **Project header:** colour band, name, label, a status summary, **+** (new session in the project root) and a **⋯** menu: Tasks…, Open folder, VS Code, Close project. Closing untracks it and hides its closed sessions; a new session there brings it back.
- **Kept until removed** (2026-10-21, replaces stars): every session stays in its project's list, whether it's running, dormant (its process ended: idle with nothing showing it, a tab closed, a crash; shown as "ready", and a click resumes it) or anything else.
  - **Remove** (right-click) moves it to the project's closed sessions and ends its process tree, background tasks included. It asks first when that stops work: it's working, waiting on the user, or has background tasks.
  - `/exit` counts as removing. Resuming brings a session back into the list.
  - Only removed sessions are pruned after the retention period, and only they can be deleted.
  - **Minimise** folds a card to its title bar: the ▾/▸ toggle in the title bar's left edge (shown on hover, always on minimised cards), right-click, or ⋯ → Minimise all for a project. It opens by itself while the session needs the user. The hover preview opens only from a card's body, never its title bar, so minimised cards have none.
  - Closed sessions don't take room in the list: the project header shows "N closed" (in place of "N open"), and it opens a menu of them, newest first with their age. A click reopens one (resume); ✕ deletes it.
  - **Force end** kills a stuck session's tree (SIGKILL) and leaves it in the list.
  - Project headers show no status dot or flash: attention belongs to sessions. Drawer tiles keep theirs, since the drawer hides the sessions.
- **Within a project:** starred first, then open sessions by start time, then closed ones (collapsed to a "n closed" line unless starred).
- **Card details:** after a ~300 ms hover, the card is drawn expanded exactly over itself (an overlay that ignores the mouse), so hover keeps following the real cards; moving to another card swaps it immediately. Card height never changes. Session actions live in a right-click menu (rename, copy ID, end, remove).
- **Tasks from an issue tracker:** per-project `[project.tasks]` in `projects.toml`: `connector` (claude.ai connector name, e.g. "Atlassian"), `query` (plain English, e.g. "Jira issues in project ACME assigned to me that aren't done") and optional `tools` (allowed MCP tool names; defaults per connector are read-only). `cc-tasks` runs `claude -p` with only those tools allowed (`--permission-mode dontAsk`, no built-in tools) and returns JSON `[{id, title, status, url, summary}]`. Picking a task starts a session in the project with a first prompt built from the task (passed via `CC_SIDEBAR_PROMPT_FILE`, so no quoting goes through wt.exe). Trackers without a connector (e.g. Azure DevOps) go through a CLI instead: `tools` holds permission rules such as `Bash(az boards query:*)`, and `cc-tasks` runs from the project folder. Write commands are refused (dontAsk); Claude Code still allows plain read-only commands.

### 3.13 Usage limits (M14)

A footer shows the account's 5-hour and weekly usage (% and reset time), read from the `rate_limit_event` that every `claude -p` stream-json call emits: refreshed by each Haiku recap, plus one tiny call at startup (`cc-usage`). Past a reset time the row dims until the next update.

### 3.14 Sessions hosted in tmux (M20, 2026-10-20)

`session_mode` in config.toml, set from Settings → General → "Run sessions in":
- **`terminal`** (default): as before. Claude Code is the tab's process, and closing the tab ends it.
- **`tmux`**: `claudes` runs Claude Code in its own tmux session `cc-<tag>`, on a private socket (`tmux -L cc-sidebar`) with the sidebar's config (`~/.config/cc-sidebar/tmux.conf`: no prefix key, since Claude uses Ctrl+B; no status bar; mouse; OSC 52; extended keys; title passthrough). The tab is only a view: closing it detaches, Claude keeps running. A click focuses the tab, or opens a new tab attached to the session (`wt … wsl.exe -e tmux -L cc-sidebar attach -t cc-<tag>`).
- **`window`**: tmux as above, but sessions are shown in the sidebar's own terminal window: xterm.js through a ConPTY running `wsl.exe -e tmux attach`, one tab per session. New and resumed sessions start detached (`CC_SIDEBAR_DETACHED=1`, with the tag chosen by the app) and open there. Closing a tab or the window detaches. The window has no title bar, as in Windows Terminal: the tabs share the top row with drag space and the minimise, maximise/restore and close buttons.

**Mechanics:**
- The app writes `~/.config/cc-sidebar/host` (`tmux`) when the mode isn't `terminal`, so `claudes` typed in any terminal behaves the same. `CC_SIDEBAR_RUN_IN` overrides it (not `CC_SIDEBAR_HOST`, which cc-hook reads as the app's address).
- Inside tmux, the wrapper exports `CC_SIDEBAR_TMUX`, and cc-hook sends it as `X-CC-Tmux`.
- Every 4 s the app runs `tmux ls` per distro to tell which sessions have a terminal attached.
- Session menu: **Hide (keep running)** (`tmux detach-client -s`) and **Open in Windows Terminal**.
- End still signals Claude's PID. When Claude exits, the tmux session and any views close.

**Processes only live while they're needed** (2026-10-21). A conversation (the card) is permanent; its process is not. A tmux session with no terminal showing it, for 5 s with no new event, is ended (SIGTERM) when it has nothing to do: it's idle, new or errored, with no pending permission, nothing in the background (jobs, dev servers, background agents) and no agents running. Working, waiting-on-you and background work keep it alive. A session never prompted whose view the user closes in the sidebar's terminal window skips the 5 s wait: the close triggers an immediate check, and it ends within about a second (its card goes with it). Its SessionEnd is recorded as `idle`, and the UI treats that as **dormant**: shown and sorted as a ready conversation (green pill, ✅ alert kept), and a click resumes it. Resumed sessions start as "ready", not "new".

**Job or service** (2026-10-21, revised 2026-10-22): each running background command is classified as follows.
- **Haiku's label wins:** cc-recap is given the running commands and labels each `job` or `service` (`BACKGROUND:` line). The label is kept per task.
- **Before a label arrives:** services are recognised by their *description* (Claude writes it for people: "server", "serve", and "api", "backend", "frontend" or "localhost" when nothing speaks of waiting), plus unmistakable server commands (`npm run dev`, `vite`, `tail -f`, `docker compose up`, …). A long script's other words are ignored, since its `api-version=` once made a pipeline watcher look like a service. Then the session-wide `WAITING:` verdict, then waiting words in the description ("watch", "until", "poll", "follow", "track", …).

**Background task progress** (2026-10-21). Claude Code writes each background task's output to `<session>/tasks/<id>.output` next to the scratchpad the hooks report (`scratchpad_dir`). `jobs::watch` reads the end of each running task's file every 3 s (over \\wsl.localhost) without involving Claude. Cards show:
- each job's latest output line under its name (ANSI stripped, after the last `\r`), and a ↗ link when its output (or command) contains an http(s) URL;
- clicking a job, or the "⧗ N background tasks" count, opens its whole output following live (`tail -f`) as a tab in the sidebar's terminal window.

Items recorded without a task id (older builds, or events the app missed) get theirs from the transcript, where each background command's result says "running in background with ID: … Output is being written to: …".

**Known differences from a plain Windows Terminal tab:**
- scrollback lives in tmux (mouse wheel), so Windows Terminal's search only sees the screen;
- mouse selection goes through tmux (Shift+drag for a native selection);
- WSL shutdown or a Windows restart ends sessions (resume as before).

In the sidebar's window: Ctrl+C copies a selection, Ctrl+V pastes (an image paste sends ^V so Claude reads the clipboard), and Shift+Enter sends Alt+Enter (newline).

## 4. Testing denials

Prefer a harmless, deterministic trigger: add a test-only auto-mode rule in `dev/hooks.json` (see the "Configure auto mode" docs) that denies any command containing `CC_SIDEBAR_DENY_TEST`, then ask the test session to run `echo CC_SIDEBAR_DENY_TEST`. Verified in S4: the `autoMode.soft_deny` prose rule (read from `--settings`) denies it and emits `PermissionDenied`. It is a classifier judgement, not a regex, but it fired reliably. A plain `permissions.deny` match does not emit `PermissionDenied`.

## 5. Install and uninstall (final milestone, needs the user's approval)

- `scripts/install.sh` (WSL): installs the `claudes` wrapper, `cc-hook` and `cc-recap` into `~/.local/bin`, registers the channel, and merges the hooks into `~/.claude/settings.json` inside a clearly marked block, with a backup.
- `scripts/uninstall.sh`: restores the backup, or removes just our block.
- Windows: an MSI or NSIS installer from `tauri build`, with optional autostart.
